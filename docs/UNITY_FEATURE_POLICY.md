# Unity feature selection

Topaz prefers Unity's maintained, first-party capabilities wherever they fit the game. This applies to gameplay foundations, authoring, rendering, visual effects, animation, audio, UI, input, assets, build tooling, and profiling. We do not write replacement infrastructure simply because custom code is possible.

For every substantial system or effect:

1. **Inventory the project and Editor version.** Check the installed Unity version, active render pipeline, packages, and existing scene patterns. Search the English Unity Manual, Scripting API, package documentation, samples, and release notes for a supported solution in that version. Do not infer availability from a tutorial for an older or future version.
2. **Prefer the smallest first-party fit.** Use a core engine feature or an already installed official package when it meets the need. Consider an additional official package only when its functionality is needed now. Use Unity's normal components, import settings, authoring tools, and package APIs before building parallel tools.
3. **Check the tradeoffs.** Verify platform support, production maturity, maintenance path, licensing and public-repository rights, ease of agent automation, upgrade behavior, accessibility and input support, and measured performance where relevant. A newer API is not automatically the better choice. Avoid preview or experimental features for a critical path without a clear benefit and a fallback.
4. **Write only game-specific rules.** Unity is an engine, not a complete action RPG. Item stack limits, loot rules, talents, chest permissions, and save migrations are Topaz rules. Keep those rules in small components or plain data behind stable IDs and interfaces to Unity features. Separate immutable authored assets from runtime state and keep save formats versioned.
5. **Make changes reversible.** Do not fork or patch engine/package source. Prefer serialized Unity assets and ordinary package APIs. Isolate any custom adapter so a future Unity feature can replace it without rewriting the game state or content. Record why a custom solution was chosen and what would trigger reevaluation.
6. **Revisit at upgrades and measured bottlenecks.** Review relevant new Unity features when upgrading the Editor and before generalizing a prototype. Test the specific project on Mac and Windows; performance claims require representative standalone scenes.

Unity's [UI system comparison](https://docs.unity3d.com/6000.6/Documentation/Manual/UI-system-compare.html) describes uGUI and UI Toolkit as supported choices with different strengths. Its [ScriptableObject guidance](https://docs.unity3d.com/6000.6/Documentation/Manual/class-ScriptableObject.html) supports shared authored data, while [Unity serialization](https://docs.unity3d.com/6000.6/Documentation/Manual/script-serialization.html) covers the runtime fields used in saves. Use the [Package Manager](https://docs.unity3d.com/6000.6/Documentation/Manual/upm-ui.html) to inspect official packages and compatible versions. Use English documentation links in Topaz docs and handoffs.

The [UI design system](UI_DESIGN_SYSTEM.md) keeps exploration nearly clear and uses a small custom theme asset because uGUI has no project-wide style sheet. The title, journal, focus cue, transient health, and interaction chip remain ordinary Unity UI components. Revisit this choice if later screen count, localization, or large lists justify UI Toolkit's document layouts, shared USS styling, or virtualized lists; keep gameplay state outside the view so such a migration remains possible.

The [Character and World collection](CHARACTERS_AND_WORLDS.md) uses
Unity's existing serialization, Topaz's atomic replacement, and distinct
Character, World, and Visit records. Topaz-specific code owns cross-world
item transfers, stable IDs, and legacy migration because Unity does not
provide those game rules. One collection snapshot makes a transfer update
both its Character and World together. Revisit physical file splitting or a
transactional store only if measured collection size or write time warrants
it; either change must keep cross-record transfers atomic.

The full-screen [menu stage](plans/CHARACTER_SELECTION_PLAN.md) renders the
same rigged model and atlas as gameplay in a small authored campfire scene.
It uses Unity's Camera, URP Volumes and renderer features, Particle System,
lights, and uGUI; Topaz code only switches cameras, chooses the model, and
keeps graphics choices in sync. The stage is inactive during gameplay. A
dedicated menu camera allows bloom, depth of field, color grading, and
ambient occlusion without the transparency conflict of the earlier render
texture preview. Revisit splitting this stage into a separate scene if
menu content or loading cost grows. The Mac review still checks each look at
Topaz's actual gameplay camera and world lighting.

The [Unity reference guide](UNITY_REFERENCE_GUIDE.md) maps the current 6000.6 Editor and installed package versions to task-specific sources. Unity 6.6 changes include [Play mode without domain reload](https://docs.unity3d.com/6000.6/Documentation/Manual/domain-reloading.html) and [serialized dictionary fields](https://docs.unity3d.com/6000.6/Documentation/Manual/script-serialization-dictionaries.html); check current project settings and migration needs before applying older advice.

## Engine capabilities versus content

Unity supplies most of the **systems** below, while authored meshes, animation clips, sounds, and the choice of how they look remain content work. Read the current `Packages/manifest.json` before using an optional package. [ASSET_SOURCING.md](ASSET_SOURCING.md) lists free art families and the rights checks for this public repository.

| Need | Unity 6.6 provides | Topaz still needs |
| --- | --- | --- |
| Character rig and animation clips | Unity [imports rigged models](https://docs.unity.com/en-us/engine/6000.6/manual/assets-and-media/asset-types/models/importing/importing-model-files), maps a [Humanoid Avatar](https://docs.unity3d.com/6000.6/Documentation/Manual/AvatarCreationandSetup.html), and [retargets humanoid clips](https://docs.unity3d.com/6000.6/Documentation/Manual/Retargeting.html). The optional official [Animation Rigging](https://docs.unity3d.com/6000.6/Documentation/Manual/com.unity.animation.rigging.html) toolkit adds procedural constraints such as aim or hand placement. | A model with a usable skeleton, clips that fit its proportions, and weapon attachment points. Unity does not supply a complete game-specific character set or automatically make every third-party animation look right. The current [KayKit Adventurers](https://kaylousberg.itch.io/kaykit-adventurers) free edition includes rigs and basic clips; its separate [free animation pack](https://kaylousberg.itch.io/kaykit-character-animations) has movement, dodge, combat, and tool clips. Check exact rig compatibility and archive license before import. |
| Animation playback and sequencing | The built-in [Animator](https://docs.unity3d.com/6000.6/Documentation/Manual/class-Animator.html), [controllers](https://docs.unity3d.com/6000.6/Documentation/Manual/Animator.html), [blend trees](https://docs.unity3d.com/6000.6/Documentation/Manual/class-BlendTree.html), and [layers](https://docs.unity3d.com/6000.6/Documentation/Manual/AnimationLayers.html) control transitions; the installed [Timeline](https://docs.unity3d.com/6000.6/Documentation/Manual/com.unity.timeline.html) package is available for scripted sequences. | Topaz's movement, swing commitment, hit windows, dodge invulnerability, and harvest completion remain gameplay rules. Animation should present those states, rather than become the only source of truth for damage or saves. |
| Ground surfaces | Unity can render imported meshes with URP materials, paint [Terrain Layers](https://docs.unity3d.com/6000.6/Documentation/Manual/class-TerrainLayer.html), and paint [instanced grass details](https://docs.unity3d.com/6000.6/Documentation/Manual/terrain-Grass.html) on Terrain. | The home and clearing now use imported KayKit dirt floor meshes over their existing flat collision floors, plus sparse KayKit grass clumps. | Combat and environment effects | The built-in [Particle System](https://docs.unity3d.com/6000.6/Documentation/Manual/ParticleSystems.html), [Trail Renderer](https://docs.unity3d.com/6000.6/Documentation/Manual/class-TrailRenderer.html), URP [Volumes](https://docs.unity3d.com/6000.6/Documentation/Manual/urp/volumes-landing-page.html), and Shader Graph cover many small effects. For 1–10 visible enemies, start with a small Particle System, trail, or existing URP effect and check readability at the fixed camera angle. |
| Lighting and day/night appearance | Unity/URP supply [lights, shadows, lightmaps, probes, ambient light, and skybox settings](https://docs.unity3d.com/6000.6/Documentation/Manual/LightingOverview.html), plus [URP Volumes](https://docs.unity3d.com/6000.6/Documentation/Manual/urp/volumes-landing-page.html) for post-processing. | Choose light colors, sky and material treatment, and the time-of-day transitions. | Collision and physical motion | Built-in [3D physics](https://docs.unity3d.com/6000.6/Documentation/Manual/PhysicsOverview.html) includes colliders, Rigidbody simulation, triggers, and queries; Topaz already uses CharacterController for the player and AI Navigation for enemies. | Configure colliders on imported art and write Topaz-specific movement, attack, damage, placement, and interaction rules. Do not add Rigidbody movement to the current player merely because a model is rigged. |
| Anti-aliasing | URP includes [FXAA, SMAA, TAA, and MSAA](https://docs.unity3d.com/6000.6/Documentation/Manual/urp/anti-aliasing.html). The first [KayKit art study](studies/KAYKIT_ART_STUDY.md) now uses the free pack library and selected models in the Mac scene. Revisit Visual Effect Graph if an authored gameplay slice needs many layered or simultaneous effects and measurement supports the added package and workflow.
